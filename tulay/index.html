tulay _

A bridge from a browser to a program on your own machine. Direct, encrypted, nothing lost on the way, and no cloud carrying the bytes.

Cooking Version 0.1.0. It runs every day in one home. There is no download yet.

What it is

Tulay is Tagalog for bridge. It is one small program that runs in the background on the machine that serves your web app, the way Ollama runs in the background for models. A page your app has already signed in opens a direct connection to it, and over that connection asks for the app's own files (a photo, a video, a document) and gets exactly what HTTPS would have given it, byte for byte.

Your app never touches WebRTC. The person looking at the page installs nothing.

The problem

You keep something big at home: a photo library, say, on a machine in a closet. To reach it from a browser anywhere, you put it behind a tunnel or a reverse proxy run by somebody else. That is a good way to get a name, a certificate and a sign-in page.

It also means every photo leaves your house, goes to a data centre, and comes back, even when the laptop asking for it is in the next room. The relay sees every byte, sets the speed, and is one more thing that has to be up.

The sign-in is small and can keep going that way. The files don't have to.

The two paths

How it works

  1. The page signs in to your app as it does today, over HTTPS.
  2. The page makes a WebRTC offer and posts it to your app. The offer holds addresses and key fingerprints, never a file.
  3. Your app checks who is asking and hands the offer to tulay on the same machine, with a grant: which local server to ask, which paths are allowed, one header to send with every request (your app's own short-lived token), and for how long.
  4. tulay answers. Both ends try every pair of addresses at once and keep the first that works: the home network when you are home, a hole punched through the two routers when you are away.
  5. The page asks for a path over the channel. tulay checks it against the grant, asks your app on loopback, and streams the answer back, ending with its length and SHA-256. The page shows nothing until both match.
  6. If the channel cannot form, or drops, or an answer does not match, the page uses HTTPS for that request and tries the direct path again a minute later. Nobody sees an error.

So your app stays the only thing that decides who may see what. Its own checks run on every request, whichever path carried it. tulay is transport.

What it will not do

  • Relay. There is no TURN server. A connection is direct or it is not used, and HTTPS carries the request.
  • Serve anything itself. Every byte comes from your app's own local server, through your app's own checks.
  • Take a grant from another machine, or carry a request to one. Its API listens on loopback only and refuses anything that arrived through a browser or a proxy.
  • Decide who someone is. It has no accounts and no sign-in.
  • Keep anything but a log of counts and kinds of path. No addresses.

What it looks like

For a person, four words:

tulay install     run it at login, and say what is left to allow
tulay status      who is connected, how each path formed, how much went
tulay doctor      why a path would not form, and what to click
tulay uninstall   stop running it at login

Every way this can fail is silent: a firewall drops the packets, a privacy switch is off, a router refuses. So doctor checks each one and names the setting. On a machine whose firewall has not been told about tulay yet it prints this (the addresses here are examples):

· running       tulay 0.1.0 (pid 4127), /usr/local/bin/tulay
· listening     udp 192.168.1.20:8852
· internet      the internet sees it as 203.0.113.7:8852; the router keeps the port, which punching likes
✗ firewall      on in stealth mode, and tulay is not on its list: packets to it are dropped
                → System Settings › Network › Firewall › Options: +, choose /usr/local/bin/tulay, Allow incoming connections (once: the allow follows tulay's signature)
· home network  tulay may send to other machines here
· connections   0 now, 0 connected

For a program, one call on loopback. Your app passes on the page's offer and says what this viewer may ask for:

POST http://127.0.0.1:8852/v1/offer

{ "sdp": "<the page's offer>",
  "grant": { "upstream": "http://127.0.0.1:3420",
             "allow":    ["/photos/pic", "/files/*"],
             "header":   ["authorization", "Bearer <your app's token>"],
             "who":      "someone",
             "secs":     43200 } }

→ { "sdp": "<the answer, for the page>" }

For the page, one function. tulay hands your app a small script, tulay.js, to serve from its own origin:

import { load } from '/tulay.js';

const r = await load('/photos/pic?id=42');
// r.via is 'p2p' or 'https'; r.body is the same bytes either way

What a machine needs

  • A Mac. Running at login and the doctor's checks are written for macOS. Nothing else has been tried.
  • The firewall's allow, once, if the firewall is on. macOS silently drops packets for a program that is not on its list. The allow holds across updates only when every build is signed with the same certificate.
  • Local Network permission, which macOS asks for, so it may talk to other devices in the house.
  • Nothing on the router. No port forward. To learn its own internet address tulay asks a public STUN server (Cloudflare's, unless you name another or turn it off). That server sees an address and nothing else.
  • An app that already works over HTTPS, with two small doors added: one that gives a signed-in page a ticket, one that passes its offer to tulay.

Where it runs today

One place: a family photo library, served from a Mac at home. The grid of pictures and the screen-sized ones come straight from that Mac to whoever is signed in. Full-size originals and videos still take HTTPS, for the reason in the second row below.

At home, on Wi-FiDirectThrough the relay
One picture169 ms406 ms
One big file3.3 MB/s11.4 MB/s
Opening the channel0.3 to 0.5 snot needed

Measured once, in one house, on one laptop, in November 2026. Not a benchmark.

Honest limits

  • Big files are slower than the relay today. Small ones arrive sooner, but a long transfer runs at about a third of the relay's speed on Wi-Fi. The congestion control in the SCTP library underneath starts slowly and grows slowly. This is the next thing being worked on.
  • Away from home is not measured yet. Hole punching works on many networks and not on all. Where it fails, the page stays on HTTPS.
  • It only fetches. A page can ask for a path and read the answer. It cannot send a form or upload over the channel.
  • A request cannot be cancelled once asked. If the page moves on, the answer still arrives and is dropped.
  • macOS only, and one machine's worth of experience.
  • No download and no licence yet. See below.

Where the code is
